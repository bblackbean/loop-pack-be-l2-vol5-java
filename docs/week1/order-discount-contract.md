# 모호한 쿠폰 요구를 구현 가능한 설계로 바꾸기

## 1. 기존 동작 관찰

`ContractClassificationTest` 로 실제 요청을 보내 확인한 값.

| # | 입력 | HTTP status | `meta.result` | `errorCode` | `data` |
|---| --- | --- | --- | --- | --- |
| 1 | `/api/v1/examples/{존재하는 id}` | 200 OK | `SUCCESS` | 없음 | **있음** |
| 2 | `/api/v1/examples/abc` | 400 Bad Request | `FAIL` | `"Bad Request"` | 없음 |
| 3 | `/api/v1/examples/-1` | 404 Not Found | `FAIL` | `"Not Found"` | 없음 |
| 4 | `/api/v1/not-mapped-at-all` | 404 Not Found | `FAIL` | `"Not Found"` | 없음 |

### 1-1. 응답 본문

```json
1. {"meta":{"result":"SUCCESS"},"data":{"id":1,"name":"예시 제목","description":"예시 설명"}}
2. {"meta":{"result":"FAIL","errorCode":"Bad Request","message":"요청 파라미터 'exampleId' (타입: Long)의 값 'abc'이(가) 잘못되었습니다."}}
3. {"meta":{"result":"FAIL","errorCode":"Not Found","message":"[id = -1] 예시를 찾을 수 없습니다."}}
4. {"meta":{"result":"FAIL","errorCode":"Not Found","message":"존재하지 않는 요청입니다."}}
```

- 3과 4는 status와 `errorCode`가 같다. `message` 문자열만 다르다.

## 2. 기준 문장과 출처

> **구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 이후에도 유지된다.**

**출처**: 1주차 과제 명세("이번 주에 정해진 입력 · 확인된 제품 약속")

## 3. 요구 분류

### 3-1. 확인된 사실 (제품 약속)

요구 문장에 직접 적혀 있는 내용이다. 어떤 구현을 택해도 지켜야 한다.

| # | 사실 | 근거 |
| --- | --- | --- |
| F-1 | 구매자는 주문 **확정 전에** 보유 쿠폰을 적용할 수 있다 | 기준 문장 |
| F-2 | **확정된 할인 금액은 이후에도 유지된다** (정책·가격이 바뀌어도) | 기준 문장 |

### 3-2. 실습 장면의 조건

이번 구현 범위를 좁히기 위하여 임시로 둔 판단이다. 틀리면 되돌릴 수 있어야 한다.

| # | 조건                            | 되돌릴 때 영향 범위                                     |
| --- |-------------------------------|-------------------------------------------------|
| C-1 | 한 주문에 쿠폰 **한 장만** 적용한다        | 복수 허용 시 쿠폰 간 **적용 순서와 중복 할인 정책**이 새로 필요해진다.     |
| C-2 | 할인액은 0원부터 주문 원금 사이여야 한다       | 배송비·세금·포인트가 들어오면 식이 확장된다.                       |
| C-3 | 같은 주문·쿠폰 재요청은 **첫 결과를 재사용**한다 | 매번 새로 계산하는 방식으로 바꾸면 네트워크 재시도에서 할인이 중복 적용될 수 있다. |
| C-4 | 쿠폰 만료 여부는 **요청 시작 시각**으로 판단한다 | 처리 완료 시각 기준으로 바꾸면 처리가 긴 경우 결과가 바뀐다.             |

### 3-3. 제품 담당자에게 물을 질문

질문 선정 기준은 **"답에 따라 사용자 응답 · 저장 데이터 · 권한 중 하나 이상이 달라지는가?"** 이며, 
달라지지 않으면 질문이 아니라 내가 직접 고르면 되는 항목이다. 이 기준으로 후보를 걸러 아래 5개를 남겼다.

| # | 질문                                          | 답에 따라 달라지는 것                                                                         |
| --- |---------------------------------------------|--------------------------------------------------------------------------------------|
| Q-1 | 구매자 외에 **운영자도 남의 주문에 쿠폰을 적용**할 수 있는가?       | **권한** · **저장 데이터** — 운영자가 가능해지면 누가 적용했는지를 기록해야 한다. 지금은 적용자가 곧 주문 소유자라 남길 필요가 없다.    |
| Q-2 | 쿠폰을 적용한 주문을 **취소하면 그 쿠폰을 다시 쓸 수 있는가?**      | **저장 데이터** — 사용 상태를 플래그로 둘지 이력으로 둘지 <br> **사용자 응답** — 취소 뒤 쿠폰함에 그 쿠폰이 다시 보이는지        |
| Q-3 | **만료된 쿠폰**과 **남의 쿠폰**을 요청자가 구분할 수 있게 알려주는가? | **사용자 응답** (다음 행동이 달라짐)                                                              |
| Q-4 | 이미 적용한 쿠폰을 **해제할 수 있는가?**                   | **사용자 응답** — 해제 엔드포인트가 새로 필요해진다. <br> **저장 데이터** — 쿠폰 상태를 되돌려야 하므로 Q-2와 같은 문제로 이어진다. |
| Q-5 | 할인액에 소수점이 생기면 **반올림인가 버림인가?**               | **저장 데이터** (최종 금액)                                                                   |

### 3-4. 도구 제안 처리

출처 없는 제안을 제품 정책으로 채택하지 않는다.

| 제안 | 출처 | 처리 | 이유                                                                                          |
| --- | --- | --- |---------------------------------------------------------------------------------------------|
| 제품 질문 후보 8개 | 요구 문장에 근거 없음 | 부분 채택 | "답에 따라 응답·데이터·권한이 달라지는가" 기준으로 5개만 선별. 나머지 3개(필드명 표기법·패키지 위치·테스트 프레임워크)는 제품 질문이 아니라 판단해 제외 |
| `INV-001`~`INV-006` 문장·반례 초안 | 주제와 출처 구분은 과제 명세, 표현은 초안 | 검토 후 채택 | 반례가 규칙을 정확하게 만드는지 직접 확인하고 문장 수정                                                             |
| 정책 자체를 바꾸는 제안 | — | 해당 없음 | —                                                                                           |

## 4. 불변식과 반례 : `INV-001` ~ `INV-006`

| 규칙 ID | 주제 | 출처 구분                           | 규칙                                                                                                                                                    | 깨지는 입력 (반례) | 기대 결과 | 책임 후보 |
| --- | --- |---------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------| --- | --- | --- |
| `INV-001` | 소유권 | 제품 약속 (F-1)<br>제품 질문 (Q-1)      | 할인 적용은 그 주문을 소유한 구매자가 자신이 보유한 쿠폰으로 요청할 때만 성공한다. 주문이든 쿠폰이든 소유자가 아니면 대상의 존재를 드러내지 않고 실패한다.                                                                                                                     | 주문 `#100`의 소유자가 `userA`인데 `X-USER-ID: userB`로 `POST /api/v1/orders/100/discount` 요청 | `404 Not Found`. 응답 어디에도 주문이 존재한다는 단서가 없다. 할인은 적용되지 않는다. | `Order`(주문 소유자 검증) / `Coupon`(보유자 검증) / 인증 계층 |
| `INV-002` | 쿠폰 개수 | 제품 약속 (F-1)<br>실습 조건 (C-1)<br>제품 질문 (Q-2, Q-4) | 확정 전 한 주문에 동시에 적용된 쿠폰은 최대 한 장이다. 이미 쿠폰이 적용된 주문에 다른 쿠폰을 적용하면 기존 쿠폰은 해제되고 새 쿠폰으로 교체된다.                                                                                       | 쿠폰 `A`가 적용된 주문에 쿠폰 `B`를 적용했더니 할인 내역이 2건이 되고 할인액이 합산됨 | 할인 내역은 항상 1건. `A`는 미사용 상태로 돌아가고 `B`만 적용된다. `finalAmount`는 `B` 기준. | `Order`(적용 쿠폰 수와 할인 상태) |
| `INV-003` | 금액 경계 | 실습 조건 (C-2)<br>제품 질문 (Q-5)     | 성공한 할인 적용 후 항상 `finalAmount = originalAmount - discountAmount` 이고 `0 ≤ discountAmount < originalAmount` 이다. 따라서 `0 < finalAmount ≤ originalAmount`이다. 즉 최종 결제 금액은 최소 1원 이상이다. | 원금 10,000원 주문에 100% 할인 쿠폰을 적용해 할인액이 정확히 10,000원이 되는 경우. `≤` 로 쓰면 통과하고 `<` 로 쓰면 실패하는 **경계값**이라, 이 반례가 부등호를 정하도록 강제한다 | 적용에 실패하고 주문의 할인 금액과 최종 금액은 변경되지 않는다. | `Order`(할인 금액 경계 검증 및 최종 금액 계산) |
| `INV-004` | 확정 결과 보존 | 제품 약속 (F-2)                     | 주문이 확정된 뒤에는 쿠폰 정책이나 상품 가격이 바뀌어도 저장된 `discountAmount`와 `finalAmount`가 변하지 않는다.                                                                         | 10% 쿠폰으로 확정한 주문이 있는 상태에서 쿠폰 정책을 20%로 변경한 뒤 그 주문을 다시 조회 → 금액이 달라져 있음 | 확정 시점 금액 그대로. 조회를 몇 번 하든 값이 변하지 않는다. | `Order` |
| `INV-005` | 중복 요청 | 실습 조건 (C-3)                     | 같은 주문·같은 쿠폰으로 다시 요청하면 저장된 첫 결과를 그대로 돌려주며, 할인 효과가 누적되지 않는다.                                                                                            | 동일한 요청을 연속 2회 전송 → `discountAmount`가 2배가 됨 | 두 번째 응답이 첫 번째와 동일. 할인 내역은 1건 유지. | `Order` / 요청 식별(`orderId` + `couponId`) |
| `INV-006` | 만료 경계 | 실습 조건 (C-4)                     | 쿠폰 만료 여부는 요청을 받은 시각 기준으로 한 번만 판단하며, 처리 도중 만료 시각이 지나도 결과가 뒤집히지 않는다.                                                                                    | 만료가 `23:59:59`인 쿠폰에 대해 요청 시작은 `23:59:58`, 처리 완료는 `00:00:01` → 완료 시각으로 판단하면 만료로 거절됨 | 요청 시작 시각 기준으로 유효하므로 적용 성공. | 요청 시각을 고정해 도메인에 넘기는 계층 / `Coupon`(만료 판정) |

## 5. 외부 계약과 내부 경계

바깥에 공개할 약속(`method` · `path` · 사용자 식별 · `request` · `success` · `error meaning`)을 정하고, 그 뒤에 감출 세 가지 결정(오류 구분 방식 · snapshot vs 재계산 · 책임 경계)을 남긴다.

### 5-1. 외부 계약

| 항목 | 값                                                                                                         |
| --- |-----------------------------------------------------------------------------------------------------------|
| **method** | `POST` — 주문의 상태를 바꾸므로 조회가 아니다.                                                                            |
| **path** | `/api/v1/orders/{orderId}/discount`                                                                       |
| **사용자 식별** | `X-USER-ID` 헤더. 이 값이 주문 소유자와 다르면 `INV-001`에 걸린다.                                                          |
| **request** | `{ "couponId": 123 }` — 쿠폰 한 개 (C-1)                                                                      |
| **success** | `200` + `meta.result = SUCCESS` + `data`에 `orderId` · `originalAmount` · `discountAmount` · `finalAmount` |
| **error meaning** | 5-2절 표                                                                                                    |

```http
POST /api/v1/orders/{orderId}/discount
X-USER-ID: {userId}
Content-Type: application/json

{ "couponId": 123 }
```

```json
{
  "meta": { "result": "SUCCESS" },
  "data": {
    "orderId": 100,
    "originalAmount": 10000,
    "discountAmount": 1000,
    "finalAmount": 9000
  }
}
```

> 실패 응답에는 `data` 키가 없다. `null`이 아니라 키 자체가 빠진다(1장). `data: null`을 기대하고 짠 클라이언트는 깨진다.

### 5-2. Error Meaning

| 상황 | 관련 불변식 | HTTP status | `errorCode` | 요청자의 다음 행동 |
| --- | --- | --- | --- | --- |
| 주문 없음 | — | 404 | `ORDER_NOT_FOUND` | 주문 목록에서 다시 고른다 |
| **남의 주문** | `INV-001` | **404** | **`ORDER_NOT_FOUND`** | 위와 **의도적으로 동일**. 주문 존재를 숨긴다 |
| 이미 확정된 주문 | — | 409 | `ORDER_ALREADY_CONFIRMED` | 할인은 불가. 주문 상세로 이동 |
| 쿠폰 없음 | — | 404 | `COUPON_NOT_FOUND` | 내 쿠폰함에서 다시 고른다 |
| **남의 쿠폰** | `INV-001` | **404** | **`COUPON_NOT_FOUND`** | 위와 동일. 쿠폰 존재를 숨긴다 |
| 만료된 쿠폰 | `INV-006` | 409 | `COUPON_EXPIRED` | 다른 쿠폰을 고르도록 유도 |
| 할인액이 원금 이상 | `INV-003` | 409 | `DISCOUNT_EXCEEDS_ORDER_AMOUNT` | 금액이 더 큰 주문에 쓰거나 다른 쿠폰 선택 |

**설계 근거**

- `errorCode`에는 업무 의미를 담고, HTTP 상태 이름(`"Not Found"`)은 재사용하지 않는다. 재사용하면 1장에서 본 것처럼 서로 다른 실패가 같은 값으로 겹쳐진다.
- `404`가 두 번 반복되는 것은 의도한 결과다. `INV-001`에서 주문 존재를 노출하지 않기로 했으므로, "없음"과 "남의 것"은 요청자 입장에서 구분되면 안 된다. 구분해 주면 ID를 바꿔가며 남의 자원이 있는지 캐낼 수 있다.
- `409`는 "요청은 이해했지만 지금 상태에서는 안 된다"는 뜻으로 썼다. 입력이 틀린 게 아니므로 `400`이 아니다.

### 5-3. 세 가지 결정

#### 결정 ① 오류를 구분하는 방식

| | 내용                                                                                                                                                         |
| --- |------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **선택** | **안정된 업무 에러 코드** (`COUPON_EXPIRED`, `ORDER_ALREADY_CONFIRMED` …) 를 `errorCode`에 담는다. HTTP status는 큰 분류만 담당한다.                                              |
| **버린 대안** | 불변식마다 예외 클래스를 하나씩 만드는 방식                                                                                                                                   |
| **이유** | 1장에서 관찰한 문제를 반복하지 않기 위해서이다. 기존 API는 `errorCode`에 HTTP 상태 이름을 그대로 넣어서, 대상이 없음(3)과 경로가 없음(4)이 둘 다 `"Not Found"`로 뭉개졌다. 쿠폰 적용은 실패 종류가 여섯 가지라 같은 방식으로는 더 심해진다. |

#### 결정 ② 확정 금액 — snapshot 저장 vs 조회 시 재계산

| | 내용 |
| --- | --- |
| **선택** | 할인 적용 시점의 `originalAmount` · `discountAmount` · `finalAmount` 를 주문에 저장(snapshot) 한다. |
| **버린 대안** | 조회할 때마다 현재 쿠폰 정책과 상품 가격으로 **재계산** |
| **이유** | **`INV-004`(확정 결과 보존)를 지키려면 재계산으로는 불가능하기 때문이다.** 재계산 방식에서는 쿠폰 정책을 10%→20%로 바꾸는 순간 이미 결제된 과거 주문의 금액까지 함께 바뀐다. 이는 `INV-004`가 금지하는 상태다. |

#### 결정 ③ 호출 순서를 숨길 책임 경계

| | 내용 |
| --- | --- |
| **선택** | `order.applyDiscount(coupon, requestedAt)` **하나를 입구로 둔다.** 소유자 확인 · 확정 여부 · 쿠폰 유효성 · 기존 쿠폰 교체 · 할인액 계산과 경계 검증 · snapshot 고정을 모두 `Order` 안에서 처리한다. |
| **버린 대안** | Facade가 `쿠폰조회 → 검증 → 할인계산 → 저장` 순서를 직접 조율 |
| **이유** | 버린 쪽에서는 **호출자가 여섯 불변식의 검사 순서를 알아야 한다.** 할인 규칙이 하나만 바뀌어도 호출하는 쪽을 함께 고쳐야 하고, 새 호출 경로(배치·이벤트)가 생기면 같은 순서를 다시 구현해야 한다. 순서를 한 곳에 가두면 바깥이 알아야 할 개념이 `주문`과 `쿠폰` 둘로 줄어든다. |

**버린 대안** — Facade가 조율. 호출자가 4단계를 안다.

```mermaid
flowchart LR
  R0["호출자"] --> R1["쿠폰 조회"] --> R2["소유자·만료 검증"] --> R3["할인 계산"] --> R4["저장"]
```

**선택** — Order 안에서 처리. 호출자는 1단계만 안다.

```mermaid
flowchart LR
  C0["호출자"] -->|"applyDiscount()"| C1["Order"]
  C1 -.-> C2["검사 · 계산 · snapshot 6가지<br/>(바깥은 모름)"]
```

버린 쪽은 호출자가 네 단계와 그 순서를 알아야 하고, 택한 쪽은 호출 한 번으로 끝난다. 바깥이 알아야 할 개념이 몇 개인지를 기준으로 삼았다.

생각해 볼 점은 이 선택이 `Order`를 무겁게 만든다는 것이다. 노출하는 개념보다 감추는 결정이 더 많을 때만 의미가 있는데, 지금은 여섯 불변식을 감추고 메서드 하나만 노출하므로 조건을 만족한다고 봤다. 감출 것이 줄어들면 이 경계는 다시 검토해야 한다.
